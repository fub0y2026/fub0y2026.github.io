源码分析

入口&配置

src/app.js— 应用入口。创建 Express 实例，设置 EJS 模板引擎，挂载中间件（express.json、urlencoded、cookie-parser、静态资源），把四个路由模块都挂在 / 下，监听 0.0.0.0:3000。

src/config.js — 全局配置中心，所有模块共享同一个对象。生成随机 JWT 密钥；维护 signingState（当前生效密钥、版本号）；定义 featureFlags（导出/调试/审计开关）；定义 diagnosticStore（reference 临时存储）。核心隐患是 configRefresh()：用普通对象 rotation 判断 rotation.pending，被原型污染后会把签名密钥替换成攻击者可控的值。

工具

jwt.js :只封装了 signToken()，用 signingState.active 作密钥签 HS256 token。验签逻辑不在这里，在中间件里

merge.js:递归深合并函数 deepMerge，自带"防原型污染"过滤（黑名单 + sanitizeKey 去点 + 限深 6）。但 constructor/prototype 只在 depth < 3 拦截，且允许递归进 function 类型，这就是原型污染的入口。

中间件

auth.js：两个守卫：authMiddleware 从 cookie 取 token 用当前密钥验签，挂到 req.user；adminMiddleware 只检查 req.user.role === 'admin'（密钥可控后可被伪造绕过），后面那段 rateCtx 是无实际作用的干扰代码

路由

auth.js：注册/登录/登出。用内存对象 users 存账号（明文密码）。注册时给每个用户预置了4 层嵌套的 settings.notifications.digest.channels结构 —— 正是这层深度让原型污染能把 constructo

user.js：普通用户功能区，也是污染触发面：

  • /dashboard、/directory、/api/search — 公告板和员工目录展示
  • POST /api/settings — 调deepMerge(user.settings, req.body)，原型污染注入点
  • GET /api/system/healthcheck — 无需鉴权就调 configRefresh()，触发密钥轮换
  • /api/export、/api/debug/config — 受 featureFlag 控制，默认关闭（污染 flag 可开启的隐藏面）

admin.js：

  • GET /admin — 过 admin 守卫后，生成一个随机 32 位hex 的 reference 存进 diagnosticStore（120 秒 TTL、一次性），渲染到 admin 页面。这是拿 reference 的地方。
  • /api/admin/login、/api/admin/promote — 都是禁用的幌子接口

diagnostic.js：最终命令执行点：

  • POST /api/reports/execute — 双守卫（auth+admin），校验 reference 的 TTL/一次性，通过后执行 execSync('/readflag') 返回结果 —— flag 出口
  • /api/reports/run、/download — 同样是禁用的幌子

解题思路

代码多了点，但思路还是挺明显的

在user.js 的 /api/settings 用 merge.js 注入污染 → 污染 config.js 里configRefresh 的 rotation.pending （即污染密钥）→ 无鉴权的 healthcheck 把密钥换成已知值 → jwt.js/auth.js 的验签和admin 判断被伪造绕过 → admin.js 发 reference → diagnostic.js 执行 /readflag。

InkVerse

InkVerse是一个功能丰富的社区博客平台，支持文章发布、赞赏打赏、内容审核、文章导出以及每周摘要报告等功能。平台最近完成了一次大规模架构升级，引入了后台任务队列和分级公告系统。作为受邀的安全顾问，你的任务是对该系统进行全面评估。试试 /api/docs

总结：
漏洞点：

  • POST /api/tip 存在竞态条件
    余额检查和扣款/加声望不是原子操作，并发后可以“超扣余额”，把普通用户刷成 reviewer。
  • Feature-Token 泄露在导出文件里
    reviewer 能导出文章，导出内容里直接给了 Feature-Token，于是能合法调用 /api/review/feature。

逻辑链：

  1. 先从 /api/docs 拿到完整接口面。
  2. 利用 /api/tip 的竞态把普通用户刷成 reviewer。
  3. 用 reviewer 审核另一个普通用户的文章并导出。
  4. 从导出文件里拿到 Feature-Token。
  5. 用这个 token 把该普通用户的文章设成 featured。
  6. 切回那个作者访问 /bulletin，拿到 featured_authors 级别公告里的 flag。

Crypto

lattice_oracle(LWE向量暴力枚举+AES)

这题的核心点是根据``A（系数）和 b（结果），反推 s`

a_i · s 是点积。如果没有噪声 e_i，这就是普通的线性方程组，直接高斯消元就能解。加了噪声 e_i∈ {-1,0,1} 后，理论上变成了「困难问题」——这是后量子密码学的基础。

真实世界的 LWE 之所以安全，是因为 s 的维度 n 很大（几百上千）、取值范围很广。但这题里：

  • n = 6 太小了
  • s 的每个元素只在 0~3 之间，只有 4 种取值

所以全部可能的 s 只有 4^6 = 4096 种。直接暴力枚举每一种 s，代入所有 30 个方程检验：如果对所有 i，(b_i - a_i·s) mod 97 都落在 {-1, 0, 1}（即 mod 97 后是 {0, 1, 96}）里，那这个 s 就是正确的秘密。

找到 s 后，按和题目一模一样的方式算出 AES 密钥，解密即可。

three_friends( RSA 多素数共享模数攻击)

三个模数共享素数：每个素数都被用了两次，三个模数两两之间共享一个素数。

  • n1 = p × q
  • n2 = q × r
  • n3 = p × r

关键点： 可以通过求最大公因数（GCD）来恢复素数

  1. 恢复素数：gcd(n1, n3)=p、gcd(n1, n2)=q、gcd(n2, n3)=r，三个 1024 位大数的 gcd 瞬间算出 512 位素数，而且 p*q==n1、q*r==n2、p*r==n3 校验全部通过。
  2. 解密三段：每段拿到对应的两个素数后，正常走 RSA 流程——算 φ = (p-1)(q-1)，求 d = e⁻¹ mod φ，再 m = c^d mod n。
  3. 拼接：三段明文转字节拼起来就是完整 flag
