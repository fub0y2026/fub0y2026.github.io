Java的反序列化漏洞有一些时基于第三方jar包的，所以我们不难免会设想是否存在不依赖第三方的Gadget。比如这条JDK7u21的链子，不需要任何其他的jar包。

没有CC依赖，那之前的InvokerTransformer，chainedTransformer，LazyMap等都不能使用了。

其实学习这个链就是主要学习它的思路，毕竟这么老的链实战中怎么可能用到

在JDK原生反序列化中能利用的类

① BadAttributeValueExpException 系列

触发方法：readObject() → 调用 toString()

可用版本：

  • JDK 8u76 之前直接可用。
  • 新版本可用代理类或可序列化对象绕过。

② TemplatesImpl

触发方法：newTransformer()

可用版本：

  • JDK 8u251 前基本可用，之后需绕过模块封装限制。

③ AnnotationInvocationHandler

触发方法：readObject() → 代理对象方法调用

可用版本：

  • JDK 8u71 前可直接用，之后受限制，但在同模块可用

④ BeanContextSupport / BeanContextServicesSupport

触发方法：readObject() → 自动添加成员

利用点：

  • 在反序列化时会调用 initialize(), readChildren() 等。
  • 可用来调用任意方法（Jdk7u21 链）

⑤ PriorityQueue

触发方法：readObject() → 调用 heapify() → siftDown() → compare()

可用版本：

  • 一直存在，但 comparator 类必须可用

⑥ HashMap / Hashtable

触发方法：readObject() → put() → 调用 key 的 hashCode() 或 value 的 equals()

⑦ java.rmi.server.UnicastRef / UnicastRef2

触发方法：readObject() → RMI 远程调用

利用点：

  • 可发起远程连接（配合 JNDI 注入）。

版本要求：

  • JDK 8u121 前 RMI 注入链可用

⑧ JdbcRowSetImpl

触发方法：readObject() → connect() → setDataSourceName() → JNDI lookup

版本要求：

  • JDK 8u181 前默认可打，之后 JNDI 限制变严

常用组合技

模板链 1（加载字节码执行）

  • PriorityQueue 反序列化时触发 compare() → 调用 TemplatesImpl.newTransformer() → 加载恶意类。

模板链 2（JNDI 注入）

  • 反序列化触发 toString() → 调用 JdbcRowSetImpl.connect() → 触发 JNDI。

模板链 3（动态代理）

  • 动态代理触发方法 → 调用目标对象方法 → 执行恶意类。

修复

之所以7U21能使用，最关键的一点就是由于sun.reflect.annotation.AnnotationInvocationHandler中的**this.type属性没有做限制**，导致可以是任何对象，但其实在readObject函数中，原本有一个对this.type的检查，在其不是AnnotationType的情况下，会抛出一个异常。但是，捕获到异常后没 有做任何事情，只是将这个函数返回了，这样并不影响整个反序列化的执行过程；在新版中，将 return; 修改成throw new java.io.InvalidObjectException("Non-annotation type in annotation serial stream"); ，这样，反序列化时会出现一个异常，导致整个过程停止，我们就不能将this.type属性设置成我们前面说的恶意TemplatesImpl对象了

只不过p神也说了，这个修复方式看起来击中要害，实际上仍然存在问题，这也导致后面的另一条原生利用链JDK8u20
